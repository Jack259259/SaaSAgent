## 1. 背景与目标

### 1.1 背景

现有 SaaS 系统承载资金计划业务作业,已具备业务配置、业务流程作业(计划编制、调整、执行)、业务审批、报表等完整功能。系统沉淀了五类高价值内容,但分散在不同载体中,用户与运营、研发人员只能各自人工查找和操作:

1. **页面操作知识** —— 系统怎么用、每个业务操作怎么一步步完成;
2. **业务文本知识** —— 业务制度、口径说明、操作手册、FAQ;
3. **IT 设计文档知识** —— 需求、概要/详细设计、接口文档;
4. **代码** —— 前端、后端、SQL、算法;
5. **数据库数据** —— 各租户的业务数据本身。

### 1.2 目标

构建统一的智能助手 Agent,将上述五类内容融合为一个对话入口,支持:

- **问答**:业务口径、系统用法、设计与实现逻辑的提问,均能给出有出处的回答;
- **取数**:自然语言查询业务数据,返回表格/图表与可核对的 SQL;
- **操作**:对系统页面操作给出分步指导、页面内引导,直至代用户自动完成(带确认与审批);
- **诊断**:跨能力组合解决复杂问题(典型如"这张报表的数为什么对不上"——需要同时查数据、查代码逻辑、查业务口径);
- **成长**:具备 Skill 体系与分层记忆,能通过反思把成功经验沉淀为可复用资产,越用越好。

### 1.3 关键技术选型(已定)

| 模块 | 选型 |
|---|---|
| 代码检索分析 | 词法检索(Zoekt/ripgrep)+ 符号图(tree-sitter/LSP) |
| 数据库取数 | WrenAI(MDL 语义层 + NL2SQL) |
| 知识库 RAG | LightRAG(业务文本知识库、IT 设计文档库) |
| 页面操作 SOP | Playwright 录制 → 参数化 SOP 资产 → 确定性执行器 |
| Agent 架构 | 自研薄编排循环,融合 Plan&Execute、ReAct、Reflection;**不引入 LangGraph 等重框架** |

## 2. 设计原则

1. **能力 ≠ Agent**:四个能力都是独立模块,但只有真正需要"上下文隔离 + 多步试错"的才升格为子 Agent(代码检索);其余做成工具或确定性执行器。避免"多 Agent 税"。
2. **编排靠 tool-use,不靠前置分类器**:主 Agent 把全部能力作为工具挂在手边,在一个推理循环里自行决定调用与组合,天然覆盖跨能力问题;不做"先分类再派发"的硬路由。
3. **资产先行**:Agent 的能力上限由四类资产决定——代码索引/符号图、MDL 语义层、知识图谱库、SOP 库。资产全部入 git、走评审、可回放、可度量,当代码管理。
4. **安全是底座不是补丁**:统一身份透传、检索前 ACL 过滤、写操作多道闸、全链路审计,贯穿每一次工具调用;多租户隔离绝不破例。
5. **框架无关的接缝**:工具契约、状态 schema 自行定义为内部接口;未来若出现长时任务/复杂图需求,可只迁移编排薄层(届时再评估 LangGraph),不动能力层。
6. **确定性优先**:能用确定性手段的(SOP 执行状态机、SQL 干跑校验、schema 校验)不交给 LLM 自由发挥;LLM 负责理解、规划与生成,执行与校验尽量确定化。
7. **可观测、可评估、可回归**:每个能力有金标评估集,上线走回归门禁;线上全链路 tracing。

## 3. 总体架构

### 3.1 分层视图

```
┌───────────────────────────────────────────────────────────────┐
│ 接入层   Web 聊天窗 / 业务页面侧边栏 /(预留)IM·IDE           │
│          SSE 流式 · 计划卡片 · 确认卡片 · 引用跳转 · 引导高亮  │
├───────────────────────────────────────────────────────────────┤
│ 编排层   主 Agent(自研薄循环)                                │
│          Plan&Execute × ReAct × Reflection                     │
│          Skill 按需加载 · 记忆/经验注入 · 预算控制 · 并行调度  │
├───────────────┬──────────────┬───────────────┬────────────────┤
│ 知识库 RAG    │ 数据库取数   │ 代码检索分析  │ 页面操作 SOP   │
│ LightRAG      │ WrenAI       │ 子 Agent      │ 查询工具       │
│ 【工具】      │ 【工具+自纠】│ 【隔离上下文】│ +确定性执行器  │
├───────────────┴──────────────┴───────────────┴────────────────┤
│ 共享底座  统一身份与权限透传 · 审计日志 · 共享工作区          │
│           记忆服务 · 经验库 · Skill 库 · LLM 网关 · 观测      │
├───────────────────────────────────────────────────────────────┤
│ 资产层    代码索引+符号图 · MDL 语义层 · 知识图谱库           │
│           SOP 库(git)· 评估集 · 提示词版本                  │
└───────────────────────────────────────────────────────────────┘
```

### 3.2 能力粒度判定

| 能力 | 形态 | 判定理由 |
|---|---|---|
| 知识库 RAG | 工具 | 单趟"检索→重排→返回片段",无多步试错,主 Agent 拿片段自行推理 |
| 数据库取数 | 工具(内置自纠小循环) | NL→SQL→干跑→自纠→执行是固定短循环,封装在工具内即可,不需独立上下文 |
| 代码检索分析 | **子 Agent**(隔离上下文) | 天然多步探索(grep→读文件→跟符号→再 grep),中间读入大量与主对话无关的代码,必须隔离,只回传结论+证据 |
| 页面操作 SOP | 查询=工具;执行=**确定性执行器** | 查 SOP 是检索;执行有副作用、需暂停确认、需可恢复——状态机比 LLM 放养可靠,且天然抗提示注入 |

### 3.3 一次典型请求的运行过程(示意)

以跨能力诊断问题"华东大区 6 月资金计划执行率报表的数对不上"为例:

1. 编排器判定为复杂任务,生成计划(① 取数核对明细 → ② 查业务口径文档 → ③ 查报表计算代码 → ④ 综合定位),计划卡片流式展示给用户;
2. 步骤①调用取数工具:WrenAI 生成 SQL → 校验层注入租户/数据范围谓词 → 干跑 → 执行 → 明细与汇总入共享工作区;
3. 步骤②调用 RAG 工具(业务库),取回"执行率口径"的定义片段及出处;
4. 步骤③派发代码子 Agent:在隔离上下文中检索报表服务的计算逻辑,回传结论+代码证据(文件:行号);
5. 编排器行内反思:核对三方信息是否自洽,发现口径差异(如"是否含在途资金")即可定位;
6. 组装回答:结论 + 数据表格 + 口径出处 + 代码证据,关键论断带引用;
7. 会话结束后异步触发事后反思,沉淀"报表对不上类问题的排查路径"经验条目。

## 4. 编排器设计(Plan&Execute × ReAct × Reflection)

编排器是自研薄循环(百行级),三种模式不是三选一,而是按任务复杂度分层融合。

### 4.1 三种模式的融合方式

**ReAct 是地板**:所有任务都跑在"思考→行动(调工具)→观察"的基础循环上。简单任务(单能力、意图明确,如"什么是资金计划占用率")不生成显式计划,直接 ReAct 一两步出答案——靠系统提示约定,不引入独立分类器。

**Plan&Execute 是复杂任务的外层**:命中以下任一信号即先规划再执行——跨能力、预计多步(>3 次工具调用)、包含写操作、用户显式要求"帮我完成某事"。计划是结构化对象(步骤、能力提示、依赖、是否需确认),以卡片流式展示;含写操作的计划必须经用户确认后才进入执行。每个计划步骤内部仍是一个小 ReAct 循环(一步往往也要多次工具往返)。步骤产物写入共享工作区,供后续步骤引用。每步结束做轻量校验,失败或出现新信息触发 replan(优先局部修补,整体重排兜底)。

**Reflection 在两个时机生效**:

- **行内反思(执行中)**:每个关键产物过校验器——确定性校验优先(SQL 干跑、SOP 后置校验、引用覆盖率、输出 schema 校验),必要时 LLM 自评(critique→revise);失败带错误信息回流重试,默认上限 2 次,全程留痕。
- **事后反思(任务级)**:任务终态(成功/失败/放弃)异步触发反思作业,产出经验条目与改进建议,详见第 8 章。

### 4.2 运行状态 schema

```yaml
AgentState:
  ids: { session_id, trace_id, tenant_id, user_id }
  user_ctx: { roles, permissions, data_scope }      # 全链路透传,工具侧二次校验
  mode: react | plan_execute
  messages: [...]                                    # 压缩后的对话窗口
  plan:
    version: n                                       # 每次 replan 递增
    steps:
      - { id, goal, capability_hint, depends_on, status, needs_confirmation }
  workspace:                                         # 跨步骤共享的中间产物(摘要+句柄)
    items:
      - { key, type: sql_result|code_evidence|doc_chunks|sop_run, ref, summary }
  scratchpad: 当前步骤的思考与工具往返(步骤结束即压缩进 workspace)
  budget: { max_steps, max_cost, used_steps, used_cost }
  reflection: { inline_retries, verdicts: [...] }
```

### 4.3 上下文工程

- **大对象不进上下文**:工具返回统一为"摘要 + 工作区句柄",模型需要细节时再按句柄分页读取(如 SQL 结果只回 schema+前 N 行+统计摘要);
- **子 Agent 隔离**:代码探索的全部中间噪音留在子 Agent 自己的上下文里,主上下文只收结论与证据;
- **滚动压缩(compaction)**:计划步骤结束即压缩该步 scratchpad;长会话对早期轮次做摘要替换;
- **注入预算**:系统提示(含 Skill 索引、记忆 TopK、经验 TopK)与单次工具结果各设 token 上限,超限截断并留句柄。

### 4.4 预算、停止与降级

终止条件:答案完成且校验通过 / 步数或费用预算耗尽 / 用户打断 / 连续 N 步无新信息(防打转)。预算耗尽时输出已确认的部分结论+未尽事项,不硬编。高峰期可降级:复杂任务限流排队、关闭事后反思、切小模型做摘要类内部调用。

### 4.5 并行与流式

无依赖的工具调用并行执行(如同时查业务库 RAG 与取数);计划步骤间按 `depends_on` 拓扑并行。全程 SSE 流式:计划生成、每步进度、工具调用摘要、最终回答分段推送,用户可中途打断或修改计划。

## 5. 能力模块设计

### 5.1 代码检索分析子 Agent

**定位**:回答"这段逻辑在哪实现、谁调用了它、报表/算法是怎么算的"一类问题;服务对象默认为内部研发与支持角色(见 9.1 能力×角色矩阵),不向租户终端用户暴露源码。

**索引管线(离线 + CI 增量)**:

```
git 多仓(前端 / 后端 / SQL / 算法)
  ├─ Zoekt:trigram 词法索引(正则/标识符精确检索,毫秒级)
  ├─ tree-sitter:AST 解析 → 符号表 + 定义/引用/调用边 → 符号图存储
  ├─ (可选增强)LSP / SCIP 导出:编译器级精确的跨文件跳转
  └─ repo map 生成:在符号图上做重要度排序(Aider 思路),
     产出可装进给定 token 预算的"仓库地图",用于子 Agent 开局定向
代码提交 → CI webhook → 增量重建索引(分钟级生效)
```

**子 Agent 工具集**:`search_code`(词法/正则)、`find_definition`、`find_references`、`find_callers`、`read_file(path, range)`、`get_repo_map(scope)`。

**协议**:输入 `{question, scope?, evidence_required}`;输出 `{answer, evidences: [{file, line_range, snippet}], confidence, followups}`。主 Agent 只见这个输出,不见探索过程。子 Agent 自带预算(最多 M 次工具调用 / N tokens),超限返回部分结论与建议。

**语义向量索引暂不上**(与选型一致:代码场景词法+符号图更可靠)。预留接口,触发再评估的条件:概念式查询("鉴权逻辑在哪")的命中率持续低于阈值。

### 5.2 数据库取数(WrenAI)

**定位**:自然语言查询资金计划业务数据,只读。

**语义层(MDL)建设** —— 这是取数准确率的第一决定因素,由数据团队维护、入 git 评审:

- 模型:表 → 业务对象(资金计划、计划版本、计划科目、组织、审批单、执行流水……【待补全量清单】);
- 指标:统一口径定义(如 执行率 = 执行金额 / 计划金额),含同义词与业务术语表;
- 维度:组织、期间、科目、币种、计划版本等;
- few-shot:历史高质量"问句-SQL"对入库,持续从线上采纳样本回补。

**调用链(工具内自纠小循环)**:

```
question + user_ctx
  → WrenAI 生成 SQL(语义层 + few-shot)
  → 我方校验层:语法解析 → 只读断言(禁 DML/DDL)→ 表白名单
      → 自动注入租户 + 数据范围谓词(RLS)
  → EXPLAIN / 干跑 → 失败则带错误回流自纠(≤2 次)
  → 只读账号执行(statement timeout + LIMIT)
  → 输出:LLM 摘要 + 表格 + 图表建议 + 展示最终 SQL 供核对
```

字段或口径有歧义时不猜,返回结构化澄清选项。同语义问句+同权限的结果做短 TTL 缓存。自然语言问句、最终 SQL、行数、耗时全部入审计。

### 5.3 知识库 RAG(LightRAG)

**库划分**:`business_kb`(业务文本)与 `it_design_kb`(IT 设计文档)两个实例/命名空间。编排器按问题性质选库,也可并查;IT 设计库仅对内部角色开放。

**摄取管线**:解析(docx/pdf/wiki,表格保真)→ 清洗 → LightRAG 插入(实体/关系抽取建图,用小模型+批处理控制成本)→ 元数据打标(来源、版本、生效日期、ACL 标签)。文档变更走增量 insert/delete;带鲜度字段,过期内容检索降权。

**检索**:LightRAG 双层检索(local 实体级 + global 主题级)混合,可叠加 rerank。**ACL 过滤必须发生在检索前**(按元数据过滤候选),不靠生成后兜底——LightRAG 原生不带多租户 ACL,由我方在存储元数据与检索入口包一层。

**引用强制**:返回片段带来源与位置;编排器约定关键论断必须有引用,无据则明示"未在知识库中找到依据"。

### 5.4 页面操作 SOP

**资产生产线**(录制为主、语义为辅、回放保鲜):

```
预发租户(种子数据)Playwright codegen 录制 + trace(含网络捕获)
  → AI 转参数化 SOP 草稿:提取 role/testid 定位、具体值泛化为 {{参数}}、
     观测到的接口与 payload 落入 api 块、从 GET 推断枚举来源
  → 人工补语义层:name / aliases / 业务前置 / 成功判定 / 是否需确认
  → schema 校验 + 静态交叉校验(接口存在性、testid 存在性)
  → PR 评审 → 发布入 SOP 库(git)
```

SOP 资产结构(preconditions / inputs / api / ui.steps / postconditions / on_failure / meta)详见附录 B。

**三种消费模式,同一份资产**:

1. **文字指导**:渲染 `ui.steps[].instruction` 为分步说明,参数填空;
2. **页面内引导**:前端引导组件(driver.js 类)按 `target` 在用户真实页面逐步高亮——前提是前端补齐稳定 `data-testid` 锚点;
3. **自动执行**:交给确定性执行器。

**执行器(确定性状态机服务,非 LLM 放养)**:

- 输入 `{sop_id, params, user_ctx}`;执行身份 = 发起用户(短时令牌代持),权限即用户权限,杜绝服务账号越权;
- 流程:preconditions 核验(权限 + 调 API 验业务前置)→ 逐步执行(**优先走 api 块**;无 API 的步骤走无头 Playwright 工作池)→ `confirm` 步暂停,挂接自家审批/工作流引擎完成"确认-恢复"→ postconditions 回查确认真成功 → 产出运行报告(关键步截图 / 响应摘要)入审计;
- 失败处理:任一步失败即停并按 `on_failure` 提示,不"猜着继续";SOP 标注幂等性,决定可否重入;
- **漂移检测**:CI 每晚在预发环境回放全量 SOP,失败自动标 stale 并在 Agent 侧下线该操作 + 告警——这套回放同时就是 E2E 回归测试集。

### 5.5 通用基础工具层(v0.2 新增)

四大领域能力之外,对标 Claude Code / Codex / OpenClaw / hermes-agent 等前沿 harness 的共性工具带,补一层**领域无关的基础工具**。由 orchestrator 直接持有,契约统一落 `contracts/toolspec/base/`。

#### 5.5.1 基线清单(13 件)

| 工具 | 作用 | 业界对应 | 副作用 | 治理要点 |
|---|---|---|---|---|
| update_plan | 模型显式创建/更新计划与待办,驱动计划卡片 | Claude Code TodoWrite、Codex update_plan | 无 | 计划含业务写步骤时仍走确认 |
| ask_user | 结构化澄清(选项卡片) | Claude Code AskUserQuestion | 无 | 一次 ≤3 问;能从上下文推断的不问 |
| get_page_context | 读用户当前页面路由、单据 ID、选中行等结构化上下文 | 侧边栏 / Claude in Chrome 形态共性 | 只读 | 前端注入、按 user_ctx 过滤;支撑"这张单"类指代消解 |
| read_workspace | 按句柄分页读取工作区大对象 | Claude Code Read 的工作区版 | 只读 | 单次返回限额(§4.3) |
| write_workspace | 向工作区写笔记/草稿/中间文档("文件即记忆") | Claude Code Write、deep-agents 虚拟文件系统 | 写(助手域) | 虚拟存储、租户隔离,非真实文件系统 |
| run_analysis | 沙箱内执行生成代码,对取数结果透视/对比/统计/绘图 | Bash / Codex 沙箱 exec 的企业受限版 | 只读 | 红线级隔离:无网络、无库连接、资源限额、产物回句柄 |
| export_file | 生成交付物(Excel / PDF / 报告模板) | 各 harness 文件产出 | 只读 | 产物入 workspace,审计留痕 |
| parse_user_file | 解析用户上传的 Excel/PDF(计划草稿、银行回单)入工作区 | 文件输入共性 | 只读 | 类型/大小白名单、查毒、按租户隔离存储 |
| save_memory | 当场写入用户偏好/口径(如"以后都用万元") | Claude Code # 记忆、OpenClaw memory | 写(助手域) | 写入门槛 + 脱敏(§7.2/7.3);用户可见可删 |
| schedule_task 系 | 定时订阅:定时报表、审批催办、到期提醒(含 list/cancel) | OpenClaw cron / heartbeat | 写(助手域) | 以用户身份运行、每任务预算、首次需确认、可随时退订 |
| notify | 模板化推送(站内信/邮件/IM) | 企业 agent 共性 | 写(助手域) | 仅白名单模板、订阅制、频控 |
| escalate_to_human | 转人工:生成工单 + 完整上下文移交 | 企业客服 agent 共性 | 写(助手域) | 移交内容按接收方权限脱敏 |
| web_search / web_fetch | 外部公开信息(汇率、LPR、监管政策) | 各 harness 标配 | 只读(门控) | 默认关闭;角色 + 域名白名单;内容按不可信数据处理 |

#### 5.5.2 Bash / 文件读写 / grep 这类原语去哪了 —— 按"工作面"翻译,不照搬

Claude Code 持有 Bash / Read / Write / Grep,是因为它的工作面就是开发者本机的文件系统,且单用户、用户全程在场、错了有 git 兜底。本系统是多租户生产服务,工作面是业务数据、知识、代码索引与页面 —— 同类原语必须以受控形态存在,而非全局裸工具:

| Claude Code 原语 | 本系统对应物 | 约束 |
|---|---|---|
| Grep / Glob | code-svc 的 search_code(Zoekt/ripgrep,§5.1) | 只读、限已索引代码仓、子 Agent 隔离上下文 |
| Read | code-svc 的 read_file(代码仓);read_workspace(工作区) | 只读、分页、限额 |
| Write / Edit | write_workspace(虚拟工作区);export_file(交付物) | 助手域;对业务系统的写仅经 sop-executor |
| Bash / exec | run_analysis(沙箱内执行生成代码);run_sop(对业务系统的"执行") | 沙箱强隔离;SOP 确定性状态机 |
| Task(子代理) | 代码子 Agent 派发 | 固定能力域,非任意 spawn |
| WebFetch / WebSearch | web_search / web_fetch | 默认关、白名单 |

**明确不引入**:运行时主 Agent 的裸 Bash、全局文件读写、自由浏览器驾驶(browser-use / openclaw 式)。理由:远程代码执行面、提示注入放大器(§9.5 的不可信内容一旦能诱发 shell 即全盘失守)、租户隔离与审计无法保证。注意区分:**开发态**用 Claude Code 建设本系统时当然持有这些原语;**产品运行时**的 Agent 不继承。

#### 5.5.3 落点与红线关系

run_analysis 落 `sandbox-svc`;schedule_task / notify 落 `scheduler-svc`(复用现有任务队列与消息通道);get_page_context 由 agent-gateway 前端协议承载;workspace 读写为 orchestrator 内置。助手域写类工具与"写操作只经 sop-executor"红线的关系:**对业务系统的写**仍只经 sop-executor;助手域副作用(通知、订阅、记忆、工作区)一律确认/订阅制 + 全量审计,且不得触达业务数据。

## 6. Skill 体系

### 6.1 定义与定位

Skill 是"完成某类任务的方法论资产":一个目录,含 `SKILL.md`(YAML frontmatter:name、description、触发场景;正文:步骤方法、注意事项、口径约定)及可选的 `scripts/`、`resources/`。

与其他资产的关系:**工具是原子能力,SOP 是单个页面操作的可执行资产,Skill 是编排多工具/多 SOP 完成一类业务任务的流程知识**。例如"月度资金计划差异分析"Skill:先取数对比计划与执行 → 查口径文档确认统计范围 → 差异大的科目下钻明细 → 必要时派代码子 Agent 核对计算逻辑 → 按模板产出分析报告。

### 6.2 渐进式披露(progressive disclosure)

系统提示只注入 **Skill 索引**(name + description,每个几十 token);编排器判断与当前任务相关时,调用 `load_skill` 工具加载全文进上下文。这使 Skill 库可以增长到数百个而不撑爆系统提示。Skill 内可声明依赖的工具与 SOP。

### 6.3 生命周期

草拟(人工编写 / 事后反思自动起草,见第 8 章)→ 评审 → 发布(git 版本化)→ 监控(命中率、加载后任务成功率)→ 迭代或下线。低命中或负收益的 Skill 自动进入复审队列。

## 7. 记忆系统

### 7.1 分层设计

| 层 | 内容 | 写入时机 | 读取方式 | 隔离边界 |
|---|---|---|---|---|
| 工作记忆 | AgentState + scratchpad + 压缩摘要 | 实时 | 实时 | 会话 |
| 情景记忆 | 历史会话摘要、未尽事项 | 会话结束异步抽取 | 开场注入 + 按需检索 | 用户 |
| 语义记忆(画像) | 偏好(格式/详略)、常用口径、角色、常查主题 | 抽取 + 用户显式设置 | 开场注入 | 用户 |
| 组织记忆 | 租户术语表、口径约定、业务日历 | 管理员维护 + Agent 建议 | 按需检索 | 租户 |
| 程序记忆(经验库) | 反思沉淀的"任务→有效路径"策略 | 反思管道(第 8 章) | 任务相似度检索 TopK | 产品级(脱敏)/租户级 |

### 7.2 写入与读取机制

- **写入门槛**:重要性评分 + 去重,避免垃圾记忆;冲突时新值覆盖并保留来源与时间;低频记忆带衰减/TTL;
- **读取**:会话开场注入画像 + 相关记忆 TopK(向量 + 标签混合检索);任务中编排器可主动调用 `search_memory`;
- **实现**:memory-svc 独立服务,存储 = 结构化表(画像/组织记忆)+ 向量库(情景/经验);抽取用小模型异步跑。

### 7.3 治理(多租户红线)

用户可查看、编辑、删除自己的记忆;写入前过 PII/敏感信息过滤;**跨租户绝不互见**;经验库默认产品级共享,但入库前强制脱敏(剥离租户数据样本与标识),并经审查。

## 8. 反思与经验沉淀(Reflection)

### 8.1 行内反思(执行中)

校验器优先确定性手段:SQL 干跑、SOP postconditions 回查、输出 schema 校验、引用覆盖率检查;必要时 LLM 自评(critique → revise)。失败带具体错误回流重试(上限 2 次),全部留痕入 trace。

### 8.2 事后反思(任务级,异步)

任务终态触发反思作业,输入 = 完整轨迹 + 终态 + 用户反馈(赞/踩/改写/采纳),产出三类东西:

1. **会话摘要** → 写入情景记忆;
2. **经验条目** → `{task_signature, 适用条件, 有效路径(工具序列), 踩过的坑, 耗时与成本}`,经自动评分(LLM-judge + 启发式:用户是否采纳、是否重试多次)达阈值后入经验库,高影响条目人工抽检;
3. **改进建议工单** → 检索 miss 清单、语义层口径缺口、文档缺口、SOP 缺口,派发给对应资产负责人——这是资产持续运营的输入源。

### 8.3 经验固化与数据飞轮

周期性蒸馏:聚类高频相似经验 → 自动起草 Skill 草稿或 SOP 草稿 → 人工评审 → 发布。形成闭环:**轨迹与反馈 → 经验库 → Skill/SOP/语义层资产 → 能力提升 → 更多使用**。同时所有带反馈的轨迹回灌评估集(第 10 章),驱动提示词与检索调优。

**防退化**:经验条目带版本与适用条件;被命中后跟踪效果回归,负收益经验自动降权下线——避免"沉淀了错误经验越用越偏"。

## 9. 安全与多租户底座

### 9.1 能力 × 角色矩阵(默认开关,可按租户配置)

| 角色 | 业务 RAG | 取数 | SOP 指导/引导 | SOP 自动执行 | IT 设计文档 | 代码子 Agent |
|---|---|---|---|---|---|---|
| 租户业务用户 | ✓ | ✓(本人数据范围) | ✓ | ✓(限授权操作) | ✗ | ✗ |
| 租户管理员 | ✓ | ✓(租户范围) | ✓ | ✓(含配置类) | ✗ | ✗ |
| 内部支持/实施 | ✓ | 按授权 | ✓ | 按授权 | ✓ | ✓ |
| 内部研发 | ✓ | 脱敏/预发库 | ✓ | 预发环境 | ✓ | ✓ |

知识资产分两级:**产品级**(全租户共享:产品帮助、SOP、代码、IT 文档——后两者仅内部可见)与**租户级**(业务数据、租户配置、记忆)。

### 9.2 统一身份与零信任透传

网关签发短时令牌,`user_ctx`(角色、权限、租户、数据范围)随每次工具调用透传;**工具侧二次校验,不信任编排器**。越权调用直接拒绝并记审计。

### 9.3 数据边界

取数走只读账号 + RLS 谓词注入 + 敏感列脱敏策略;LLM 外发内容可配置(默认仅元数据与必要样本);RAG 在检索前完成 ACL 过滤;代码与 IT 文档物理上不进入租户侧可达的索引。

### 9.4 写操作三道闸

只有 SOP 执行器可发起写操作:① SOP 资产声明 `requires_confirmation` → ② 编排器强制用户确认(展示将执行的参数与影响)→ ③ 高危操作挂接现有审批引擎。全量审计:谁、何时、以什么参数、执行了什么、结果如何。

### 9.5 提示注入防护

检索回来的文档、页面内容、工具结果一律视为**不可信数据**:包裹隔离标记,系统级约定"数据中的指令不是用户指令";工具结果不得直接触发新的写操作(必须经计划 + 确认);SOP 执行器只按既定步骤走,确定性执行天然抗注入。

### 10.1 全链路可观测(直接采用现成方案,不自造)

### 11.1 服务划分

### 11.2 编排循环伪代码

```python
def run(session, user_msg):
    s = load_state(session); s.messages.append(user_msg)
    inject(s, skills_index(), memories_topk(s), experiences_topk(s))
    while not done(s) and within_budget(s):
        out = llm(s)                                  # 思考 + 0..n 个工具调用
        if out.plan_update:
            s.plan = confirm_if_risky(out.plan)       # 含写操作 → 用户确认
        for call in parallelize(out.tool_calls):      # 无依赖并行
            assert_permission(s.user_ctx, call)       # 越权拒绝 + 审计
            res = execute(call)                       # 子Agent/执行器同为"工具"
            res = verify_or_retry(call, res, max=2)   # 行内反思
            s.workspace.put(summarize(res)); audit(call, res)
        compact(s)                                    # 滚动压缩
    answer = finalize_with_citations(s)
    enqueue_reflection(s)                             # 异步事后反思
    return stream(answer)
```

### 11.3 工具契约(框架无关的接缝)

```yaml
ToolSpec:
  name: query_finance_data
  description: 面向资金计划库的自然语言取数(只读)
  input_schema:  { question: string, preferred_format?: table|chart }
  output_schema: { summary, table_ref, sql, lineage }
  permission_scope: data.read.finance_plan
  side_effects: read              # read | write
  confirmation_required: false    # 写操作必为 true,编排器强制执行
  timeout_ms: 30000
  errors: [AMBIGUOUS_FIELD, NO_PERMISSION, TIMEOUT, VALIDATION_FAILED]
```

内部以 MCP 兼容形式暴露能力,便于未来接入 IDE、IM 等更多客户端而不改能力层。

### 11.4 模型策略

LLM 统一网关:重试、故障转移、限流、prompt cache。模型分级路由——规划与代码分析用旗舰模型;摘要、记忆抽取、文档摄取用小模型;模型可替换(契约层隔离,不绑定单一厂商)。

## 13. 风险与对策

| 风险 | 对策 |
|---|---|
| NL2SQL 口径错误导致错数 | 语义层先行 + 干跑校验 + 展示 SQL 供核对 + 金标集回归;歧义必澄清不猜 |

| 提示注入诱导越权/误操作 | 数据与指令隔离 + 写操作三道闸 + 确定性执行器 |
| 成本失控 | 会话预算 + 分级模型 + prompt/结果缓存 + 大对象句柄化 |

| 用户不信任、采纳率低 | 全程可见(计划卡片/SQL/引用/执行报告)+ 从只读能力起步建立信任 |

## 附录 B SOP 资产 Schema(摘要)

```yaml
id / name / description / aliases / domain
preconditions: { permissions, prerequisite_state, blocking_when }
entry: { route, page_title }
inputs: [{ key, label, type, required, validation, source(api) }]
side_effects: read|write
requires_confirmation: true|false
api:  { calls: [{ method, path, body{{参数}}, capture }] }
ui:   { steps: [{ instruction, target{testid|role|name}, action, value, confirm }] }
postconditions: { human_readable, verify{api, expect} }
on_failure: [{ when, hint }]
meta: { related, source, owner, updated, version }
```
