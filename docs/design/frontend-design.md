## 1. 背景与范围

后端 Agent 系统已按阶段 0–10 建成,通过 `POST /chat`(SSE 流式)对外提供能力。本方案在**同一个后端仓内**新建 `web/` 文件夹,用原生 HTML/CSS + Alpine.js 做一个对标 Claude 网页版的聊天前端,由后端 `agent-gateway` 作为静态资源一起伺服 —— **一次部署后端,前端随之上线**。

**本期范围**:后端仓内嵌的单页聊天界面(类 Claude),含对话、流式输出、富交互卡片、文件上传、会话历史(本地)。

**本期不做**:独立前端仓 / 独立部署 / 构建流水线;嵌入现有 SaaS 系统的侧边栏;移动端原生 App;长对话虚拟滚动等高复杂度能力(见 §3 取舍)。

**与后端的关系**:**同源同部署**。前端用相对路径 `/chat`、`/files` 调同一服务,无跨域。唯一契约接缝是后端 `docs/dev/sse-protocol.md`。

## 2. 设计原则

1. **内嵌、同源、零构建**:前端是后端仓里的静态文件夹,无打包步骤(浏览器直接加载 ES Module),由 agent-gateway 伺服;部署 = 部署后端。
2. **同源带来的简化(对比独立仓版,这些问题直接消失)**:无 CORS;身份/会话靠同源 cookie/session 天然携带;无 `VITE_API_BASE` 注入;无独立 CI/部署。
3. **对标 Claude = 学交互骨架与克制美学,不抄像素与品牌**:实现 Claude 网页版的**交互模式与信息架构**(居中对话流、流式打字、清爽留白、消息块、停止/重试、代码块、附件卡片、明暗主题);视觉用**自有设计令牌**。**严禁复制 Anthropic 商标、logo、专有字体、配色或受版权保护的图标/CSS**;图标用开源图标(Lucide,ISC),字体用可自由商用字体。
4. **前后端职责切分清晰**:前端只负责"拿文件 / 校验 / 上传 / 展示附件卡片";**文件真正解析(DOCX/XLSX→文本)由后端 `parse_user_file` 工具完成**,前端不在浏览器解析业务文档。
5. **轻量依赖,本地 vendor 即用**:不引构建工具链;少量轻量库以 `<script>` 或 ESM 方式从 `web/vendor/` 加载(Alpine、marked、highlight.js、DOMPurify)。
6. **Mock 优先,可独立验证**:开发阶段可用一个本地 mock SSE(见 §9)驱动 UI,不依赖真实后端联调;后端就绪后前端无需改动(本就是同源相对路径)。
7. **契约对齐,不臆造字段**:SSE 事件渲染严格对齐后端 `sse-protocol.md`;字段对不上的列入"待后端补充契约",不在前端假造。
8. **安全**:渲染助手输出/工具结果时 Markdown 必须 DOMPurify 消毒(禁 HTML/脚本注入),对齐后端"检索与工具内容不可信"的立场。

## 3. 能力取舍(原生+Alpine 下,明确保留与舍弃)

诚实列出代价,你可按此决定。**核心体验全部保留;舍弃的是高复杂度的工程增强项。**

| 能力 | 原生+Alpine 下 | 决定 |
|---|---|---|
| SSE 流式 / 停止 | `fetch`+`ReadableStream` 解析 + `AbortController`,不依赖框架 | **保留**(核心) |
| 富事件卡片(计划/确认/澄清/工具/引用) | Alpine 组件 + 模板渲染 | **保留**(核心) |
| 文件上传 + 附件卡片 | `fetch` multipart + Alpine 状态 | **保留**(核心) |
| Markdown + 代码高亮 | marked + highlight.js + DOMPurify(vendor) | **保留**(靠轻量库) |
| 会话历史 | localStorage(IndexedDB 可选) | **保留**(本地版) |
| 明暗主题 / 响应式 | CSS 变量 + 媒体查询 | **保留** |
| 打字机效果 / 克制动效 | 原生 + CSS | **保留** |
| **长对话虚拟滚动(500+ 条不卡)** | 原生手写成本高 | **舍弃/降级**:普通滚动 + "加载更多"分页 |
| **跨设备会话同步** | 需后端会话 API | **舍弃**(本期 localStorage,仅本机本浏览器) |
| **工程化/组件化程度** | Alpine 提供响应式与组件,但弱于 React | **降级接受**:复杂度上限低于框架版,够本期用 |
| E2E 自动化测试 | 无构建链,E2E 较弱 | **降级**:以手动验收 + 少量脚本化检查为主(见 §9) |

一句话:**功能不怎么减,核心全在;减的是工程复杂度的天花板和少数增强项。**

## 4. 技术栈(内嵌·零构建)

| 维度 | 选型 | 说明 |
|---|---|---|
| 结构 | 原生 HTML + ES Module(`<script type="module">`) | 无打包,浏览器直接加载 |
| 交互/状态 | **Alpine.js**(≈15KB,`<script>` 即用) | 提供响应式数据、组件(`x-data`)、事件、模板;补足纯原生 DOM 的组织度 |
| 样式 | 原生 CSS + CSS 变量(设计令牌) | 明暗主题、响应式;不引 Tailwind(免构建) |
| Markdown | marked(vendor) | 渲染助手输出 |
| 代码高亮 | highlight.js(vendor) | 代码块高亮 |
| 消毒 | DOMPurify(vendor) | Markdown 转 HTML 后强制消毒 |
| 图标 | Lucide(SVG 内联或 vendor,ISC 许可) | 无品牌风险 |
| 字体 | Inter + JetBrains Mono(自托管/开源) | 不用专有字体 |
| 依赖加载 | 全部置于 `web/vendor/`(本地自托管,不依赖公网 CDN) | 生产建议自托管,避免外网与合规问题 |

> 不使用 React/Vue/Vite/打包器。Alpine 是渐进增强库,script 引入即可,契合"现有仓里放个文件夹、无构建、同部署"。

## 7. SSE 集成与契约映射(核心)

前端用 `fetch('/chat', { method:'POST', ... })` 接收 `text/event-stream`,在 `sse.js` 中用 `ReadableStream` 逐块解析,按事件类型分发到 Alpine 状态。**事件名与字段以后端 `docs/dev/sse-protocol.md` 为准**,下表为阶段 2 约定基准,实施时逐字段对齐:

| SSE 事件 | 含义 | 前端渲染 |
|---|---|---|
| `plan` | 计划生成/更新 | 渲染/更新 PlanCard |
| `step` | 步骤进度 | 更新对应步骤状态 |
| `tool_call` | 开始调工具 | ToolActivity 友好文案 |
| `tool_result_summary` | 工具返回摘要 | 折叠展示摘要(大对象不展开) |
| `confirm_request` | 写操作需确认 | ConfirmCard;确认/拒绝 → `POST /chat/confirm` |
| `ask_user` | 需澄清(≤3 问+选项) | AskUserCard 选项 → 回执端点 |
| `answer_delta` | 答案增量 | 追加到流式正文,平滑打字 |
| `citation` / 引用字段 | 来源引用 | CitationList(来源+跳转) |
| `done` | 本轮结束 | 结束流、启用操作、停光标 |
| `error` | 错误 | ErrorBanner + 重试 |

**交互要点**:发送即建 assistant 占位消息,随事件流原地填充;停止用 `AbortController` 中断 SSE;确认/澄清经 `POST /chat/confirm`(或后端约定端点)续跑;重试 = 重发上一条用户消息(带相同附件引用)。**同源下这些请求都是相对路径,无跨域处理。**

### 7.5 任务进展区与工具调用可视化(顶部呈现层)

这两块**复用 §7 已解析的同一批事件**(`plan`/`step`/`tool_call`/`tool_result_summary`),不需要后端改动,只是把它们从"消息内卡片"提升为顶部专门区域的实时可视化。核心呈现模型:**顶部进展区 = 当前轮次的实时仪表盘(临时,随轮次刷新);消息流内 = 完成后的历史留痕。**

#### 7.5.1 顶部任务进展区(改动 ①)

位置:主对话区**顶部**(TopBar 之下、消息列表之上)留出一块可折叠区域,展示本轮任务的规划与执行进展。

- **何时出现**:仅当本轮收到 `plan` 事件(即编排器走 Plan&Execute)时展开;简单问答(无计划、仅 `answer_delta`)时不出现,不占空间。
- **内容**:计划步骤清单(来自 `plan`)+ 每步实时状态(来自 `step`:待执行 / 进行中 / 完成 / 失败)+ 当前焦点("正在执行第 2/3 步:核对执行明细")。`plan` 版本更新(replan)时原地刷新而非堆叠。
- **可折叠**:默认展开;用户可折叠为**一行摘要**(如"计划 3 步 · 进行到 2/3 · 正在查询资金数据 ▸"),点击再展开。避免常驻占据对话空间。
- **轮次结束**:本轮 `done` 后,进展区收起(或淡出);完整的计划 + 工具时间线作为历史**沉入该条助手消息内留痕**(与会话历史持久化一致,刷新后可回看)。
- **失败**:某步 `error`/失败时,该步标红,进展区保留以便用户看到卡在哪。

#### 7.5.2 工具调用过程与结果可视化(改动 ②)

把每次工具调用呈现为**带状态的时间线条目**,既出现在顶部进展区对应步骤下,完成后也随留痕进入消息:

- **触发**:`tool_call` → 新增一条工具条目,状态=进行中(转圈),显示**人话文案**(见下)+ 可选入参摘要。
- **结果**:`tool_result_summary` → 该条目状态转为完成(✓)或失败(✗),按下面的**折叠分档**展示结果。
- **工具名翻译**:维护工具名→友好文案映射表,例:`query_finance_data`→"查询资金数据"、`search_knowledge`→"检索知识库"、`ask_codebase`→"分析代码"、`find_sop`/`run_sop`→"查找/执行页面操作"。无映射时回退显示原名。
- **结果折叠分档(核心,按内容量分三档,不要做成"全展开"或"一律折叠")**:
  - **短结果**(摘要在阈值内,默认 ≤3 行或 ≤200 字)→ **内联直接展示,不折叠**,用户一眼看到。
  - **长文本结果**(超阈值)→ **默认折叠**,只显示**概览行 + "展开 ▸"**(如"查询资金数据 ✓ · 返回 128 行 ▸"),点击才展开完整内容。
  - **结构化大对象**(表格 / 代码 / JSON / 长列表)→ **一律默认折叠**;展开后在**受控容器内渲染**(限定最大高度 + 内部滚动),绝不把整张表或整段代码把对话顶得很长。
  - 阈值集中为可配常量(行数/字数/容器最大高度),便于统一调整。
- **折叠状态与控制**:折叠/展开状态记在每个工具条目自身(`expanded`,默认 false),用户**逐条**控制;可选提供"展开全部 / 收起全部";展开渲染时仍走 DOMPurify 消毒。
- **大对象对齐后端"摘要+句柄"**:`tool_result_summary` 本就是摘要,前端默认只渲染摘要;若需更细内容按句柄拉取,同样进折叠容器,绝不默认平铺——这既是体验也是性能。
- **不可信内容消毒**:工具结果(尤其 RAG 文档片段、取数表格)渲染必经 DOMPurify,与聊天消息同一安全标准。
- **多步/并行**:同一计划步骤内多次工具调用按到达顺序排列;并行调用各自独立条目并行更新状态。

#### 7.5.3 状态与实现

进展区与工具时间线由 Alpine 状态驱动:`currentRun{ plan:{steps[]}, toolTimeline:[{id, tool, displayName, status, argsSummary, resultSummary, expanded}], collapsed }`。事件处理在 §7 分发基础上,额外把 `plan`/`step`/`tool_call`/`tool_result_summary` 投影到 `currentRun`;`done` 时把 `currentRun` 快照并入当前助手消息的 content_blocks(留痕),再清空 `currentRun`。**纯前端状态投影,无新网络调用。**

## 8. 文件上传子系统(本期重点)

### 8.1 支持格式与前端校验

| 类别 | 格式 | 前端处理 |
|---|---|---|
| 文档 | DOCX、ODT、RTF、EPUB、HTML、MD、TXT | 仅校验类型/大小 + 上传 + 附件卡片;不在浏览器解析 |
| 表格 | XLSX、CSV | 同上 |
| 结构化 | JSON | 同上(可选预览前 N 行) |
| 图片 | JPEG、PNG、GIF | 上传 + 缩略图预览;是否送多模态见 §12 决策 |

前端校验:扩展名 + MIME 双白名单、单文件大小上限(默认 20MB,可配)、条数上限、重复去重提示。

### 8.2 文件上传 API 契约(需后端提供 —— 见 §12)

同源 multipart 上传,先拿句柄再随消息带句柄:

```
POST /files            (multipart) → { file_id, filename, mime, size, status }
GET  /files/{file_id}  → 元数据/下载(回看用)
```

发消息时 `POST /chat` 的 body 携带 `attachments: [file_id, ...]`;Agent 侧按需调 `parse_user_file(file_id)`(后端阶段 3 已建工具)解析入工作区。**同源,无 CORS。**

### 8.3 后端解析能力缺口(需回填后端 —— 见 §12)

后端 `parse_user_file` 当前覆盖 **xlsx / csv / pdf 文本**。本期以下格式**需后端补解析器**,否则前端能上传但 Agent 读不了:

> **缺解析器(按 D3 分批补)**:第一批 DOCX、MD、JSON、HTML;次之 ODT、RTF、EPUB;**图片暂不要求后端解析**,仅保留上传与缩略图,待多模态就绪再启用输入。
> 建议:DOCX→python-docx/mammoth、MD/JSON/TXT→直读、HTML→trafilatura、ODT/RTF→pandoc、EPUB→ebooklib;图片→(暂缓)OCR 或多模态。

前端不被阻塞:上传与卡片照常;对"后端尚不能解析"的格式,卡片标注"已上传,解析待后端支持",后端对未支持类型返回明确错误码,前端友好提示。

### 8.4 附件交互

整页拖拽遮罩 + 点击📎选择;上传进度;成功变附件卡片(类型图标 + 文件名 + 大小 + 移除);图片缩略图;失败可重试/移除;消息发出后附件卡片随用户消息块展示。Alpine 管理附件暂存与状态。

## 8.5 Skill 管理模块

入口位于 Sidebar 底部、"用户/设置"**上方**新增一项「Skill 管理」。这是一个 CRUD 管理界面(列表 + 弹窗 + 表单),仍用原生 + Alpine,不引新框架。

### 8.5.1 治理定位(关键 —— 决定写操作怎么落)

Skill 是**治理资产**,不是普通用户数据:后端 CLAUDE.md 红线 10 要求 `assets/skills/` 改动过 schema 校验 + 评估回归、走 git 版本化与评审;§9.1 角色矩阵将 Skill 列为产品级资产。因此前端的"管理"不能等于"点保存即生效",有两个原则:

- **权限边界**:Skill 管理入口默认**仅对管理员 / 内部角色可见可用**(按 user_ctx 角色控制),非授权用户不显示此入口。见 §12-D5 决策。
- **草稿 / 审核 vs 直接生效**:用户新建/编辑的 Skill 是"提交草稿待审"还是"直接进生效库",见 §12-D5 决策;生产环境**强烈建议草稿+审核**(Skill 正文会进 LLM 上下文,是提示注入面,不应让任意写入即时生效)。

### 8.5.2 功能与交互

| 功能 | 交互 | 说明 |
|---|---|---|
| 查看列表 | 「Skill 管理」打开管理视图(全屏面板或大弹窗):列表展示 name / description / 状态(生效/草稿/待审)/ 更新时间 | 数据来自后端 Skill 列表 API |
| 查看详情 | 点列表项 → 只读查看 SKILL.md 渲染(Markdown 经 DOMPurify 消毒) + frontmatter 元信息 | 复用 markdown.js |
| 编辑 | 详情内「编辑」→ 表单(name、SKILL.md 文本域)→ 保存 | 保存走后端更新 API;按 D5 进草稿待审,提交后提示"已保存为草稿,待管理员审核" |
| 发布生效 | 管理员在草稿/待审详情页操作「发布生效」→ 调后端 status 变更接口(draft→active) | 仅管理员;生产走审核,开发/测试环境可简化为直接生效 |
| 删除 | 列表项「删除」→ 二次确认 → 调删除 API | 仅授权角色 |
| 新建 | 「新建 Skill」按钮 → **弹窗**:输入 Skill 名称 + SKILL.md 内容(多行文本域,带实时预览)→ 提交 | 提交走后端创建 API |
| 上传压缩包 | 「上传 Skill 包」→ 选择 .zip → 上传 → 后台解压入库 → 刷新列表 | 前端只上传 + 展示结果;**解压/校验/入库全在后端** |

编辑/新建表单要点:name 前端校验(非空、字符规范);SKILL.md 文本域配实时 Markdown 预览(消毒);提交后展示后端的 schema 校验结果(失败则在表单内显示错误,不静默)。

### 8.5.3 上传压缩包(前后端职责切分 + 安全)

**前端只负责**:选择 .zip(类型 + 大小上限校验)、上传到 `POST /skills/upload`、展示上传/解压结果(成功入库哪几个 Skill,或失败原因)。

**后端负责(本期需新增 —— 见 §12-D6)**:安全解压并入库。安全要求(前端无法保证,必须后端做):防 **zip slip 路径穿越**、解压体积/文件数上限(防解压炸弹)、只接受白名单结构(一个 Skill 目录:`SKILL.md` 必需 + 可选 `scripts/`、`resources/`)、SKILL.md schema 校验、按 D5 落草稿或生效。前端对后端返回的逐条结果(成功/拒绝+原因)友好展示。

### 8.5.4 Skill 管理 API 契约(需后端提供 —— 见 §12-D6)

```
GET    /skills                  → [{ id, name, description, status, updated_at }]
GET    /skills/{id}             → { id, name, description, content(SKILL.md), status, ... }
POST   /skills                  (name, content) → 创建(草稿/生效按 D5)
PUT    /skills/{id}             (name, content) → 更新
DELETE /skills/{id}             → 删除
POST   /skills/{id}/status      (status: draft|active) → 状态变更(发布生效;仅管理员)
POST   /skills/upload           (multipart .zip) → 解压入库结果(逐条成功/拒绝)
```

后端阶段 9a 建的是 Skill **装载**(渐进式披露、load_skill),**未必含上述管理类写 API 与上传解压**;这些列为后端待补。前端可先对 mock 开发(W4 用 mock 这些端点),后端补齐后切真实。

### 8.5.5 安全

SKILL.md 是不可信输入:预览渲染必经 DOMPurify;前端不执行 Skill 内任何脚本;上传仅传 .zip 字节,解压在后端隔离进行。入口与写操作严格按 user_ctx 角色门控。

## 9. 会话历史与开发期 Mock

**会话历史(localStorage,见 §12-D1)**:前端实现会话列表、切换、重命名、删除、历史回看。`store.js` 提供 Repository 接口 + localStorage 实现(IndexedDB 可选),UI 不直接碰存储,留好将来切后端会话 API 的接缝。数据模型:`Conversation{id,title,created_at,updated_at}` 与 `Message{id,conv_id,role,content_blocks[],attachments[],created_at}`(content_blocks 支持 text/plan/tool/confirm/citation 富类型)。**按 D1 衍生要求**:历史中不写入敏感信息;在用户菜单/设置中提供「清除本地历史」选项(退出时可用),一键清空本地会话与消息。

**开发期 Mock(无构建链下的验证手段)**:`web/mock/mock-sse.js` 提供一个可切换的本地 mock —— 拦截 `/chat` 返回预设 SSE 序列(正常流 / 异常流 / 复杂任务流 / 长延迟流),用 URL 参数或开关启用。**验证以"手动验收清单 + 少量脚本化 DOM 断言"为主**(原生无构建,重 E2E 性价比低):可选用一个极简测试页 `web/mock/selftest.html` 跑关键纯函数(SSE 解析、Markdown 消毒、校验逻辑)的断言。后端就绪后关掉 mock,相对路径直接打真实后端,前端零改动。

## 10. 后端伺服与部署(同仓同部署)

**唯一后端改动**:agent-gateway 增加静态资源伺服 —— 把 `web/` 作为静态目录挂载,并对前端路由做 SPA 回退(未匹配 API 的 GET 返回 `web/index.html`)。例如 FastAPI:`app.mount("/", StaticFiles(directory="web", html=True))` 置于 API 路由之后,或用回退路由返回 index.html(确保 `/chat`、`/files` 等 API 路由优先于静态匹配)。

**部署**:无独立前端部署 —— 部署后端即带上前端。前端用相对路径调同源 API,无 CORS、无 baseURL 注入。生产建议第三方库自托管于 `web/vendor/`(不依赖公网 CDN)。

**身份**:同源下沿用后端会话/cookie 机制(见 §12-D4);开发态可注入 `X-User-Ctx`。前端不自造权限,只承载透传。

## 11. 非功能性需求(NFR)

- **性能**:首 token 尽快上屏;打字增量渲染(append,避免整列重绘);长对话用普通滚动 + 分页(已舍弃虚拟滚动)。
- **健壮**:SSE 断线可重试;上传失败可恢复;加载/空/错误三态完整。
- **无障碍**:键盘可达(Enter 发送 / Shift+Enter 换行 / Esc 停止);流式更新用 `aria-live`;对比度达 WCAG AA。
- **安全**:Markdown 经 DOMPurify 消毒;附件类型白名单;不在前端日志打印敏感内容。
- **响应式**:桌面/平板/移动自适应(CSS 变量 + 媒体查询)。
- **国际化**:文案集中(中文为主,预留)。

## 12. 决策点(已拍板)

> 状态:6 项决策全部已定(2026-06-15)。以下为最终结论与衍生的前端要求;实施以此为准。

**D1 · 会话历史存储 = localStorage(本机)+ Repository 接缝**
与"零构建、同源、快速落地"一致;同源下 localStorage 无跨域;会话历史非敏感协作数据,本地满足首期;Repository 抽象保证将来可平滑切到后端会话 API(跨设备同步时)。**衍生要求**:历史中不存敏感信息;**退出时提供"清除本地历史"选项**(见 §9)。

**D2 · 文件上传 API = 后端新增 `POST /files` + 配套元数据端点**
上传是核心闭环的硬前提(附件卡片 → 消息携带 file_id → Agent 解析)。后端提供 multipart 上传端点,返回 `{ file_id, filename, mime, size, status }`;`/chat` 接受 `attachments` 数组。同源,无 CORS 适配。前端按此契约开发(见 §8.2)。

**D3 · 解析能力缺口 = 前端全格式放开上传(仅类型/大小校验);后端按优先级分批补解析器**
**优先级**:第一批 DOCX、MD、JSON、HTML(覆盖绝大多数企业文档与结构化数据);次之 ODT、RTF、EPUB;**图片暂不要求后端解析,仅保留上传与缩略图,待多模态就绪再启用输入**。**前端行为**:上传成功后,对后端尚不能解析的格式,附件卡片标注"已上传,解析待后端支持";后端返回明确错误码时在消息流内友好提示,不阻断对话(见 §8.3)。

**D4 · 身份与 user_ctx = 完全沿用后端 cookie/session;开发态注入 `X-User-Ctx` 调试**
同源天然共享 cookie,无额外令牌逻辑;前端不自造权限,所有角色控制(如 Skill 管理入口可见性)依赖后端返回的 `user_ctx`(通过 `/chat` 或用户信息接口携带)。开发期 mock 用 header 注入模拟不同角色,不污染生产代码(见 §9、§10)。

**D5 · Skill 管理权限与生效 = 仅管理员/内部角色可见;写入进"草稿待审",审核通过才生效**
Skill 是注入 LLM 上下文的治理资产,属高危面(提示注入风险),故:**权限门控**——非授权角色连入口都不可见(前端渲染前查角色,后端 API 强制鉴权);**双态分离**——写入生成草稿(`status=draft`),不影响线上 Agent,需审核流程(后端 status 变更接口)转为生效(`active`);生产强烈建议走此流程,开发/测试环境可简化为直接生效。**前端影响**:列表展示状态(生效/草稿/待审);编辑提交后提示"已保存为草稿,待管理员审核";管理员可在详情页操作"发布生效"(见 §8.5)。

**D6 · Skill 管理 API 及上传安全 = 后端新增 CRUD + 安全 ZIP 上传/解压;前端不解析 ZIP**
后端提供(均需管理员角色鉴权):`GET /skills`、`GET /skills/{id}`、`POST /skills`、`PUT /skills/{id}`、`DELETE /skills/{id}`;`POST /skills/upload`(.zip)必须实现:**路径穿越防护**(拒绝 `../` 等非法路径)、**解压炸弹防护**(限制解压后总大小与文件数,建议 50MB / 500 文件)、**结构白名单**(每个 Skill 为一目录,`SKILL.md` 必需 + 可选 `scripts/`、`resources/`)、**SKILL.md schema 校验**、**入库策略按 D5 进草稿/待审**。**前端职责**:仅校验扩展名(.zip)与大小上限,上传后展示后端逐条目结果(成功入库 / 拒绝原因)(见 §8.5)。

> 相比独立仓版,已**移除**跨域(CORS)、`VITE_API_BASE`、独立部署、跨域令牌等决策 —— 同源内嵌后这些不再存在。
> **后端待补清单**(可与前端开发并行,前端先对 mock 开发):D2 `POST /files` + `/chat` attachments;D3 解析器分批(DOCX/MD/JSON/HTML 优先);D6 `/skills` CRUD + `/skills/upload` 安全解压 + status 变更接口。汇总入 `docs/integration/backend-gaps.md`。
